# Ludios Sense

`/ludios-sense` is available to signed-in internal users of all roles. External partner accounts cannot run scans or read scan results. The Sensor Tower token is a server-only `SENSOR_TOWER_TOKEN` secret.

Date defaults to today UTC (requested t). Discovery starts at the last completed UTC date and searches up to seven calendar dates for the latest three nonempty reporting dates. The report explicitly shows requested t, actual reporting date per store, and retrieval time. Future dates and empty country selections are rejected.

Defaults: US, Japan, Canada, Russia, Germany, Australia and United Kingdom. Discovery sends the selected ISO codes together in `regions` to `/v1/facets/metrics` with app-only breakdown, daily downloads descending and iOS/Android device filters separately. Pagination stops below 1,000 combined estimated downloads/day per store. There is no separate-country breakout trigger.

Daily history batches up to 100 app IDs and all selected countries in each weekly request to `/v1/{os}/sales_report_estimates`. Normalize by app/store/country/date first. iOS downloads are iu + au only when both components are valid. Conflicting duplicates stop the scan; identical duplicates do not add volume. Then sum a fixed basket of selected countries with any valid observation in the 28-day lookback. Countries with no observations anywhere in the lookback are explicitly reported as unavailable and omitted from both baseline and recent period. Missing days inside the basket remain gaps. This avoids newly available country data being treated as growth. Games are not combined across stores or unverified unified IDs.

Rule `1.4-aggregate` preserves the local v1.3 growth gates, weekday adjustment, zero-baseline display, and short-history traction rules. Release date is background only. Early detection includes a 3K-to-8K day-on-day increase. Aggregate growth may hide a breakout in a small individual market; this is an accepted tradeoff. Included genres follow the existing reviewable category map; broad/ambiguous games remain in the review tab.

Scans run in resumable server steps, one upstream request at a time. The initiating request starts a bounded background worker; the protected `/api/cron/ludios-sense` worker continues unfinished jobs each minute. The protected `/api/cron/ludios-sense-daily` starts the seven-country check at 21:00 UTC on the preceding day (04:00 WIB) daily; a matching manual or scheduled job is reused. Browser polling reads compact progress summaries and does not advance API work. Persistent expiring leases prevent concurrent duplicate steps, and a global upstream lease serializes requests with a one-second cooldown. Failed steps back off before retrying; token/access failures stop immediately. Native HTTPS transport enforces a 30-second timeout, never follows redirects, and sanitizes errors. Attempts are counted against a 1,000-request budget. Store metadata is refreshed after 30 days; retained candidates remain for 30 days. Country-level history is shared across selections, so narrower selections can reuse observations already retrieved for a wider selection. Explicit per-country coverage distinguishes a missing observation from a country never requested. Cached and new games are partitioned into separate batches: games with matching missing-week plans share a batch. Recent reporting windows refresh seven days for revisions; older historical windows fetch only uncovered weeks. Missing observations are tracked as queried coverage, never converted to zero. An in-flight legacy 25-app batch finishes before changing batch size. Completed ranking pages are cached for seven days, so repeat and next-day scans only retrieve uncached reporting dates; older ranking pages are revisited as their cache expires. Empty ranking responses are never cached. A completed identical scan with the current detection rules is shared across all users for the saved report’s 31-day lifetime. Partial reports are reused too, preserving the warning and avoiding repeated quota exhaustion. Different country selections have distinct reports. Removing countries for the same requested date recalculates downloads and detection signals from a completed saved superset report, using its original candidate pool, per-country observations and reporting dates, without new Sensor Tower requests. Charts use the recalculated saved observations. Source retrieval time is disclosed; partial coverage remains partial and queried missing observations remain gaps. Older narrower runs are stopped before their next request when such a saved source is available, with already attempted calls retained in the audit. Adding uncovered countries, changing the requested date, or lacking a reusable completed source follows the normal discovery and recent-window refresh path. The page uses a cache-only lookup when filters change; it may save a recalculated subset report but never starts upstream API work automatically. Up to 118 days of history and query coverage are retained per country; historical queries merge by observation date and retrieval time without replacing newer dates. A past scan reconstructs discovery for that date; cached metadata and history alone do not make a future-discovered game a historical candidate. Pausing persists a server-side control flag and stops future steps; an already submitted step may finish. Reloading the same browser session resumes the saved job. Results remain labeled with their original filters if controls change.

Persistence uses the existing private server cache table, on both Postgres/Supabase and local SQLite, under sense-prefixed keys. No new public tables, notification delivery, or changes to recovery guards are introduced. The continuation worker is independent of alert recovery guards because it only completes explicitly requested research scans. Each completed job preserves its retrieved values and sanitized request parameters. The UI receives compact game summaries and loads the selected aggregate chart from the saved result on demand; it never retrieves additional Sensor Tower data for chart selection. Full per-country history remains on the server.

Validation: detector cases, fixed-basket missing values, distributed sub-country-floor growth, recurring weekday spikes, 60 reproducible comparisons against the Python detector, authorization and input validation, warm-history refresh, concurrent lease ownership, transport deadlines, and the country-selection/report flow. Manual research remains necessary; download growth is not evidence of retention, organic demand, or commercial success.

## API allowance and estimates

A compact, collapsed-by-default “API usage” disclosure shows a pre-scan estimate for saved candidates plus a caveat that discovery pagination, new games and retries add calls. The estimate endpoint is authenticated and makes no Sensor Tower calls. First scans cannot be estimated accurately before discovery. The local monthly meter counts actual attempted Sensor Tower requests (including HTTP failures/retries), not browser status polling or cache reads. Calls before this feature was enabled are excluded and the tracking start is shown. All users share one server-side meter. `SENSE_MONTHLY_REQUEST_LIMIT` configures the allowance, default 10,000 attempted calls per UTC calendar month. Reservations occur under the existing global upstream lease before sending a request, so concurrent scans cannot overrun the allowance. Sensor Tower's `x-api-usage-count` and `x-api-usage-limit` headers are recorded separately and shown as organization-reported usage, including other teams. Their billing-unit definition is not assumed to equal this runner's request count. The monthly ledger resets by UTC calendar month; organization numbers are last-observed values, not a live quota guarantee.

At the monthly allowance, organization-reported limit, or existing 1,000-call per-run cap, no further upstream request is sent. A partial report includes only games whose history batches completed, clearly warns that other games/stores may have been missed, and preserves completed cache coverage. The thresholds, daily coverage, seven-day revision refresh, and notification scope are unchanged; notification delivery remains outside scope.

Game icons use the `icon_url` returned by existing app metadata requests. Older reports fetch missing icons only for visible rows, in batches of up to 100 apps per store. These calls share the upstream rate lock and monthly allowance, and icons (including missing icons) are cached for 30 days across users and reports. Icon retrieval does not rerun download history; unavailable or broken images show a placeholder. The report request count describes the scan; the monthly API usage meter also includes icon requests.

The shortlist groups cross-store records only when Sensor Tower supplies the same `unified_app_id`. Store download totals, growth, and signals stay separate, and each store has its own detail button. Growth-game and genre-review counts deduplicate verified matches; the evaluated count still measures store apps. The visible-row metadata cache also retains unified IDs, with a one-time metadata refresh for older icon-only cache entries. Table genre labels remove the iOS `Games/` prefix and standalone Games/Entertainment categories on both stores; source metadata, classification, and detail labels stay intact.

The daily report key and date filter use WIB calendar dates. The daily trigger at 21:00 UTC belongs to the following WIB date. Retrieval still caps discovery at the latest completed UTC reporting day, then falls back to available Sensor Tower dates. The report shows actual reporting dates and retrieval time; daily scheduling does not imply today’s estimates are available at 04:00 WIB. Shared caches are server-side and independent of user identity. No Sensor Tower calls are made by cache/status reads; optional icon metadata can still require separately metered calls.

## Recent detections

The default shortlist retains in-scope detections for seven inclusive reporting days, measured separately against each store’s evaluated date. Current signals remain available as a separate view and summary count. The watchlist reads completed, shared saved reports for the exact same country basket; it never reconstructs earlier signals from revised history, combines baskets, or reads future detections. It adds no Sensor Tower calls and works with existing completed reports. Days without saved scans do not create inferred detections.

Each retained store record shows its first and latest saved detection within the window. Current qualifying games retain their signal. Otherwise, “Holding scale” requires latest downloads at least 1,000 and a three-day average at least 80% of the last detected average (latest downloads if no average existed). Lower values show “Cooling down”; missing or insufficient observations show “Insufficient data.” Missing games remain visible without presenting old values as current downloads; their chart explicitly identifies the previous saved report. These research statuses do not alter growth thresholds, create alerts, or rerun analysis. Verified cross-store grouping stays in place.

## Local WIP: game-first browser

The shortlist now defaults to Worth attention: confirmed momentum and early warnings first, followed by games holding scale. Cooling games remain in Recent detections; genre review, unconfirmed traction, and all evaluated games have separate filters. These are presentation choices; detection and retention rules are unchanged. Verified unified IDs still group store apps, while their metrics and charts remain separate.

Cards show artwork, names, publishers, store indicators, and one status. Hover or keyboard focus opens a preview after 250 ms. Tab enters preview controls; Escape closes it. Click/tap opens a native modal detail drawer with store tabs, saved metrics, and the existing 28-day chart. Chart data is fetched only when opening a drawer. Missing retained observations are explicitly labeled, and charts use their original saved-report identifiers. Report provenance and API allowance are collapsed by default; partial coverage and filter mismatch warnings remain visible.

The renderer supports optional `screenshotUrls` supplied on game summaries, up to four validated HTTPS images in source order. There is no verified screenshot field in the current metadata integration, so no guessed upstream fields, new store requests, scraping, or forced cache refreshes are added. Existing reports show the store link when screenshots are unavailable; broken screenshots disappear without affecting metrics or charts. Future metadata integration must verify the upstream response before populating this field.

For a safe local review using illustrative icons and demo metrics, start these in separate terminals from the project directory:

```sh
node scripts/ludios-sense-dev.mjs
node scripts/ludios-sense-preview.mjs
```

Open `http://127.0.0.1:3101/ludios-sense`. The app uses a separate `.next-sense-wip` build cache so existing dev servers can keep running. The proxy binds to loopback, mocks every API response, and forwards only UI/asset requests to Next.js; it cannot run Sensor Tower scans. It changes no production configuration. To run desktop, hover, keyboard, drawer, dark-theme, and mobile checks using installed Chrome:

```sh
node scripts/verify-ludios-sense-preview.mjs
```

Screenshots are written to `../outputs/ludios-sense-wip/`. Nothing in this workflow deploys or publishes the revamp.

Saved-detection history reads the prior reports in one database batch and projects only confirmed/early detections, preserving their original reporting dates and chart source IDs. It does not transfer every old evaluated game to rebuild the shortlist. The page bounds stalled history reads to two 20-second attempts, marks attention/recent counts as incomplete while pending or failed, and offers a saved-history retry without starting a Sensor Tower scan.
